What calibration measures

To estimate e and θ from one raw sensor number, we need to measure a few things about this specific robot first — that's what calibration is, and it's exactly the 4 steps in the panel below:

  1. reflection fully over the black tape
  2. reflection fully over the white background
  3. the width of the sensor's transition region between them (± e_max)
  4. wheel speed at 100% and the track width

The model (docs/00-sim.md & 01-lqr.md)

Two numbers describe the robot: lateral offset e [mm] and heading error θ [rad]. Forward speed v and curvature κ of the line drive them:

de/dt   = v·sin(θ) ≈ v·θ
dθ/dt = ω − κ·v

ω [rad/s] is the yaw rate every controller below is choosing. The sensor can only report e inside ±e_max — outside that window the reading saturates and the robot goes "blind." That single hard number is what breaks fixed-speed LQR on sharp turns and is the whole reason MPC gets invented.

The simulated calculation

The plot above comes from this loop (JS port in this page; Python original in code/sim.py and code/run_bangbang.py):

e, theta = E_MAX * 0.7, 0.0     # start near the edge of the sensor window
log = []
for i in range(int(6.0 / DT)):  # 6 s of simulated time
    sign = 1.0 if e > 0 else -1.0
    omega = -omega_mag * sign
    log.append((i * DT, e))
    e, theta = step(e, theta, v, omega, kappa=0.0, dt=DT)

def step(e, theta, v, omega, kappa, dt):
    e_next = e + dt * v * math.sin(theta)
    th_next = theta + dt * (omega - kappa * v)
    return e_next, th_next

The control law is one line — turn one way or the other at a fixed rate, based only on which side of the line you're on. The model is two lines — lateral offset e drifts by v·sin(θ), heading error θ drifts by the commanded yaw rate ω. No solver, no matrices.

Proportional (and PD) control, entering a turn of radius R at constant speed. Push k_p up and it oscillates on entry; push it down and it settles into a large steady-state offset once it's in the turn — "corners badly." Full writeup: README, Session 2.

The simulated calculation

The plot above comes from this loop (JS port in this page; Python original in code/sim.py and code/run_pd.py):

s = e = theta = 0.0
log = []
for i in range(int(t_max / dt)):
    if s > track.length:
        break
    e_measured = measure(e, e_max)     # sensor saturates outside +-e_max
    omega = -kp * e_measured - kd * theta
    log.append((i * dt, e, theta))
    kappa = track.kappa(s)             # 0 on the straight, 1/R in the turn
    e, theta = step(e, theta, v, omega, kappa, dt)
    s += v * dt

def measure(e, e_max):
    return max(-e_max, min(e_max, e))   # sensor only sees +-e_max either side

def step(e, theta, v, omega, kappa, dt):
    e_next = e + dt * v * math.sin(theta)
    th_next = theta + dt * (omega - kappa * v)
    return e_next, th_next

Same plant model as bang-bang, plus two new pieces: measure() clips e to what the sensor can actually report (bang-bang's control law didn't need the clipped value, only its sign), and track.kappa(s) looks up how curved the line is at the robot's current position along it, so the simulated turn actually bends the line under a fixed-speed robot.

Same scenario, but the gains come from a cost function instead of a guess: pick Q_e, Q_θ, R and the Riccati equation hands back k_e, k_θ. Widen the turn radius until the verdict flips to BLIND — that's the steady-state offset e_ss = −κv/k_e breaking the sensor window. Full writeup: docs/01-lqr.md, and docs/02-mpc.md, "Where LQR runs out."

The simulated calculation

The plot above comes from this loop (JS port in this page; Python original in code/sim.py):

k_e, k_th = lqr_gains_discrete(v_cmd, dt)   # solved once, offline (Riccati)
s = e = theta = 0.0
log = []
for i in range(int(t_max / dt)):
    if s > track.length:
        break
    omega = -k_e * measure(e, e_max) - k_th * theta
    log.append((i * dt, s, e, theta, v_cmd, omega))
    kappa = track.kappa(s)
    e, theta = step(e, theta, v_cmd, omega, kappa, dt)
    s += v_cmd * dt

Same loop as P/PD — the only thing that changed is where k_e and k_θ come from. P/PD, you pick them by hand. Here, lqr_gains_discrete solves the discrete algebraic Riccati equation once, before the loop starts, and the loop never touches them again (see "Cost weights" → "Gains" above, and the derivation in docs/01-lqr.md).

Same steering law as LQR (using the gains from the LQR tab), but forward speed is re-decided every control period from a short preview of the track. Watch v(t) drop before the corner, and e(t) stay inside the window where fixed-speed LQR went blind. Full writeup: docs/02-mpc.md and docs/03-lqr-vs-mpc.md.

Equations

Steering law is identical to LQR's, just re-solved for whichever speed v is currently chosen:

ω = −k_e(v)·e − k_θ(v)·θ

What's new: v is no longer fixed. Every control period it's re-picked from a short list of candidates by minimizing a short-horizon cost:

v* = argmin_v  Σ (Q_e·e² + Q_θ·θ²)dt  +  Q_v(v−v_ref)²·N·dt

sum taken over N steps of the model above, rolled forward under the previewed curvature — see "The simulated calculation" below.

e(t) — solid red = simulated MPC, dashed blue = simulated fixed-speed LQR, solid green = your real robot's last MPC run, if any.
v(t) — MPC's speed schedule vs LQR's constant v_ref; green = real robot

The simulated calculation

The plots above come from this loop (JS port in this page; Python original in code/sim.py):

def mpc_choose_speed(e, theta, s, track, candidates, horizon,
                      dt, e_max, v_ref, q_e, q_th, q_v, pen=1e4):
    best_cost, best_v = float("inf"), candidates[0]
    for v in candidates:
        k_e, k_th = lqr_gains_discrete(v, dt)   # re-solved per candidate speed
        ep, thp, sp, cost = e, theta, s, 0.0
        for _ in range(horizon):                 # roll forward under LQR steering
            omega = -k_e * measure(ep, e_max) - k_th * thp
            cost += (q_e * ep**2 + q_th * thp**2) * dt
            cost += pen * max(0.0, abs(ep) - e_max)**2 * dt   # blindness penalty
            ep, thp = step(ep, thp, v, omega, track.kappa(sp), dt)
            sp += v * dt
        cost += q_v * (v - v_ref)**2 * horizon * dt   # prefer staying near v_ref
        if cost < best_cost:
            best_cost, best_v = cost, v
    return best_v

s = e = theta = 0.0
log = []
for i in range(int(t_max / dt)):
    if s > track.length:
        break
    v = mpc_choose_speed(e, theta, s, track, candidates, horizon, dt, e_max, ...)
    k_e, k_th = lqr_gains_discrete(v, dt)
    omega = -k_e * measure(e, e_max) - k_th * theta
    log.append((i * dt, s, e, theta, v, omega))
    e, theta = step(e, theta, v, omega, track.kappa(s), dt)
    s += v * dt

The outer loop is identical to LQR's. The new part is mpc_choose_speed: for every candidate forward speed, it re-solves the LQR gains for that speed and rolls the model horizon steps into the future using the previewed curvature, scoring how much error and "blindness" that speed would cause. The candidate with the lowest predicted cost wins, its first move gets applied, and the whole search reruns next control period — a receding horizon.
